P-1.3 power-loss leg: NBD FLUSH does not fsync (syscall-level proof)
=====================================================================
Date: 2026-07-27. Host: Oracle Linux 9.3, viperblock engine served over
NBD (native Go server, same vb.Flush path the nbdkit plugin calls),
file backend, WAL on xfs SSD.

Method: strace -f -tt -e trace=fsync,fdatasync on the serving process;
qemu-io as NBD client issued 1 write, a 2 s settle pause, then 50
explicit NBD_CMD_FLUSH commands in a tight burst.

Result (2026-07-27_flush_no_fsync.strace, copy-pasted):
  3274290 11:23:27.847964 fsync(5) = 0     <- server open/recovery
  3274290 11:23:27.859571 fsync(5) = 0     <- server open/recovery
  3274294 11:23:30.846920 fsync(5) = 0     <- 200 ms background syncer,
                                              after the single write
  (the 50 FLUSH commands ran 11:23:32.848915 .. 11:23:32.865599)
  -> ZERO fsync-family syscalls during 50 guest flushes.

Conclusion: vb.Flush() -- the barrier NBD/virtio FLUSH and therefore
every guest fsync maps onto -- moves data from the memory buffer into
the WAL file's page cache but NEVER fsyncs it. A host power loss (or
host kernel crash) within the background syncer's window loses writes
the guest was told were flushed. This violates the durability contract
a block device's FLUSH implies, independent of the (separately measured)
memory-ack window.

Fix target: Phase 1 gate P1.4 ("guest FLUSH is a durable barrier"),
alongside the F2 replicated-WAL work. The verification rig for the fix
should be a volatile-cache FUSE filesystem (buffer writes in memory
until fsync, drop-on-signal) so the loss/no-loss count can be measured
directly on one host; design noted in the project STATUS backlog.
